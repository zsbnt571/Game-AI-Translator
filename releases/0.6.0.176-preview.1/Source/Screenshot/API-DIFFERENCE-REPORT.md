# 0.2.3 与 0.2.6 API请求差异

## 相同项

- API地址：`https://api.deepseek.com/v1/chat/completions`（实机日志）。
- 模型：`deepseek-v4-flash`（实机日志）。
- `stream=false`，无`response_format`，`temperature=0.15`。
- 未设置`max_tokens`。
- 都使用静态共享`HttpClient`和`SocketsHttpHandler`；连接超时10秒、连接池生命周期5分钟。
- 都使用`ResponseHeadersRead`，收到响应头后读取完整普通JSON正文。
- 同一截图均为一次批量请求，不逐行请求；没有额外自动重试。

## 不同项

| 项目 | 0.2.3 | 0.2.6 | 0.2.7处理 |
|---|---|---|---|
| 批量输入 | JSON数组`[{id,text}]` | `[[GRPxxx]]`文本标记 | 恢复0.2.3 JSON数组 |
| system prompt | 要求自然翻译并只返回严格JSON | 要求保留segment marker | 恢复严格JSON |
| user prompt | 翻译完整段落，按ID返回JSON | 每个Group保留标记并在标记下输出 | 恢复紧凑JSON |
| 返回解析 | ID对象/包装对象/数组容错JSON | 正则切分`[[GRPxxx]]` | 恢复JSON容错解析 |
| 缺失项重试 | 最多可能重试缺失项 | 单次，无重试 | 保持单次、不自动重试 |
| 首字节超时 | 早期版本只受完整60秒限制 | 独立首字节超时，默认30秒 | 保留0.2.6机制 |
| 完整超时 | 60秒 | 可配置，默认90秒 | 保留0.2.6机制 |

## 实机日志证据

- 0.2.3成功样本：5段、363个原文字符；约511ms收到HTTP 200响应头，6099ms完整结束，响应2913字节。
- 0.2.6慢样本：5组、358个原文字符；约458ms收到HTTP 200响应头，首字节等待26455ms，26929ms完整结束，响应13506字节。
- 因此27秒不发生在OCR、请求发送前或等待响应头。实际延迟集中在HTTP 200之后等待首个正文数据；同时返回包比0.2.3约大4.6倍。唯一相关协议变化是由严格JSON切换为`[[GRP]]`标记输出。
- 0.2.7没有删减原文：同一输入的原文字符数保持不变，只更换封装协议和提示词。

记录原文字符数、完整请求字节数、发出时间、响应头相对耗时、首字节相对耗时、完整正文相对耗时、响应字节数和返回字符数。API Key不写入日志。
